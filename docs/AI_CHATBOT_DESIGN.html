AI Chatbot Architecture

k8s-cluster-health SRE Assistant
🎯 Chatbot Vision
An intelligent SRE assistant that understands cluster health, performs troubleshooting, executes remediation, and learns from the knowledge graph. Combines LLM reasoning with deterministic tools and semantic search.
Core Capabilities
🔍 Semantic Search
Query the knowledge graph using embeddings. "What are the security risks?" → finds related nodes across components.
⚙️ Tool Execution
Analyze pods, get logs, query Prometheus, execute kubectl commands, create tickets.
💭 Reasoning
Multi-step problem solving: analyze symptom → query graph → fetch data → propose solution → execute.
📊 Context Awareness
Maintains conversation state, knows prior incidents, understands cluster baseline.
Key Design Principles
  • Safety-First — All destructive actions require confirmation. Read-heavy by default.
  • Explainable — Every recommendation shows reasoning chain and source (which node, which metric).
  • Feedback Loop — Learns from user corrections. If user says "that diagnosis was wrong," updates embeddings.
  • Graph-Driven — Uses the k8s-cluster-health knowledge graph as the source of truth for architecture.
  • Tool-Native — Tools are first-class. LLM decides *whether* to call a tool, *which* one, and *how*.

🧠 Embedding Model Architecture
Uses embeddings to convert unstructured queries into vector space for semantic search across the knowledge graph. Combines with BM25 (keyword) search for hybrid retrieval.
Embedding Pipeline
Query to Results: Embedding Flow
Embedding Model Choices
✅ all-MiniLM-L6-v2 (Recommended)
Dimensions: 384
Speed: ~10ms per query
Accuracy: 0.93 (NDCG)
Cost: Self-hosted (free)
Best for: Production, real-time queries
🚀 OpenAI text-embedding-3-small
Dimensions: 512
Speed: ~100ms (API call)
Accuracy: 0.96 (NDCG)
Cost: $0.02 per 1M tokens
Best for: Highest quality, one-off searches
Hybrid Search Strategy
Why Both Vector + Keyword Search?
Semantic (Vector): Captures meaning. Query "pod won't start" matches node "CrashLoopBackOff".
Keyword (BM25): Captures exact terms. Query "prometheus" matches nodes with "prometheus" in label/desc.
Combined: Re-rank top-K from vector search using BM25 score. Get best of both worlds.
Embedding Storage & Indexing
1
Pre-compute: On each `/graphify update`, compute embeddings for all new/changed nodes using the embedding model.
2
Store in Qdrant/Pinecone: Vector DB with 1M-scale capacity. Index by node_id for fast lookup.
3
Cache hot queries: Redis cache recent embedding vectors (expires 24h). Hit rate ~70%.
4
Fallback to re-embed: If cache miss, re-compute embedding on-the-fly (<10ms).
Query Enhancement
Query Expansion
User: "Pod keeps crashing"
→ Expanded query: "Pod CrashLoopBackOff restart failure container error exit code"
Technique: LLM generates synonyms + related terms, embed expanded query.
Benefit: Better recall for synonymous concepts.
🔄 Complete Request-Response Flow
Walk through a real incident diagnosis scenario from first message to final recommendation.
Scenario: Collector Pod Crashing
1
User Message: "collector pod in default namespace keeps restarting. What's wrong?"
2
API Gateway: Validates auth, logs request, forwards to orchestrator with trace ID.
3
Orchestrator Receives: Loads conversation history (if exists), initializes context with system prompt.
4
LLM Decides: "Need pod status + logs. Should also check architecture for error patterns."
5
Tool Calls Issued (parallel):
• get_pod_status(namespace="default", pod_name="collector-*")
• search_knowledge_graph(query="collector error handling restart")
• get_logs(service="collector", namespace="default", since="30m")
6
Tool Router Executes: Calls kubectl, queries Qdrant, fetches Loki. Returns combined results.
7
LLM Analyzes Results:
Pod status shows: 5 restarts, OOMKilled in last cycle
Logs show: "memory exceeded 512MB limit"
Graph shows: Collector has no max_heap_size config + note about memory leak in pkg/collector/nats.go
8
LLM Formulates Diagnosis:
"Root cause is likely memory leak in NATS connection handling (per architecture docs). Recommended: increase memory limit to 1GB + investigate nats.go line 142."
9
LLM Proposes Action: "Should I scale up the memory limit to 1GB? I can do this with kubectl patch, but need your confirmation."
10
Response Sent: Full explanation with sources (which nodes from graph, which logs), recommended action, link to relevant code.
11
User Responds: "OK, go ahead and patch it" or "No, I want to investigate the code first"
12
If Action Approved: LLM calls scale_pod_memory(pod_name="collector-*", new_limit="1Gi"), confirms success, stores feedback.
13
Learning Loop: Conversation + resolution logged. Embeddings updated for future similar queries.
🛠️ Implementation Roadmap
Phase 1: Core Infrastructure (Week 1-2)
  • API Gateway: FastAPI wrapper with auth, rate limiting, request/response logging.
  • LLM Orchestrator: Claude API integration with conversation management (store in PostgreSQL).
  • Tool Router: Function-calling spec for Claude. Validates & executes tools.
  • Basic Tools: get_pod_status, query_prometheus, get_logs (read-only for safety).
Phase 2: Knowledge Graph Integration (Week 3)
  • Embedding Model: Deploy all-MiniLM-L6-v2 in a container. Pre-compute embeddings for all graph nodes.
  • Vector DB: Set up Qdrant with graph node embeddings.
  • search_knowledge_graph Tool: Hybrid search (vector + BM25).
  • Cache: Redis for embedding vectors + search results.
Phase 3: Analysis & Actions (Week 4)
  • analyze_pod_health: Call RCA analyzer API.
  • Destructive Tools: restart_pod, scale_deployment (with double-confirmation).
  • Incident Tracking: create_incident_ticket (GitHub API integration).
  • Dry-Run Simulation: simulate_fix tool for safe testing.
Phase 4: Feedback & Learning (Week 5)
  • Feedback Capture: User rates each response (thumbs up/down).
  • Embedding Updates: Negative feedback triggers re-embedding of related nodes.
  • Conversation Store: Persist all conversations for fine-tuning data.
  • Monitoring: Track tool success rates, latencies, error patterns.

Security Considerations
  • Authentication: API key + rate limiting. Multi-tenant support via namespace isolation.
  • Authorization: Tool-level permissions. Only SREs can call destructive tools.
  • Audit Trail: Every tool call logged with user, timestamp, input, output. 30-day retention.
  • Secrets: API keys stored in Sealed Secrets. LLM never sees raw credentials.
  • Prompt Injection: Strict tool schemas. LLM cannot construct arbitrary commands.
Deployment Architecture
Production Deployment
Configuration: 2 API replicas for HA + 1 embedding pod. Horizontal auto-scaling on CPU/memory. All services in same namespace for direct DNS. Ingress via existing Traefik.
