Resilience — JVM & Network
Targets the "pod dies / gets restarted / then works fine" pattern. Hetu correlates restart events with JVM memory/GC and network/DNS signals to tell you why the first start failed and the exact spec change that stops it recurring — instead of relying on a manual restart.

"Restart-to-heal" = a pod that CrashLoops or fails readiness on first start but is healthy after one or more restarts. Almost always a startup race (dependency/DNS not ready, JVM warm-up longer than the probe) or memory headroom (heap vs limit). These are fixable in the spec — manual restarts just paper over it.
Detected patterns
JVM
checkout-api — OOMKilled then stable exit 137
Heap -Xmx512m ≈ container limit 512Mi → no headroom for non-heap (metaspace, threads, direct buffers). GC thrash 1.8s pauses before kill. Heals after restart because traffic is lower on the fresh pod.
Fix: set limit 768Mi & -XX:MaxRAMPercentage=70 (drop fixed -Xmx); add startupProbe.
NET
payments-gw — connection refused to postgres at boot
First start logs: dial tcp 10.0.x:5432: connect: connection refused ×6, then succeeds. DB/sidecar not ready when app starts. Readiness flaps for ~40s.
Fix: add startupProbe + init-container wait-for-dep, or app-level retry/backoff on dependency connect.
DNS
notify-worker — intermittent SERVFAIL resolving smtp-relay.brevo.com
CoreDNS latency spikes + ndots:5 causing 4 lookups per query at startup. Resolves after retry → "works after restart". Correlates with CoreDNS CPU throttling.
Fix: set Pod dnsConfig ndots:2; bump CoreDNS replicas/limits; enable NodeLocal DNSCache.
PRB
search-api — liveness killing slow JVM warm-up
App needs ~38s to warm (class-load + cache prime) but livenessProbe initialDelaySeconds:15 → kubelet kills it mid-boot → CrashLoop until node is warm/cached.
Fix: move warm-up to startupProbe (failureThreshold×period ≥ 60s); keep liveness lean.

Suggested patch
resources:
  requests: {memory: 768Mi}
  limits:   {memory: 768Mi}
env:
- name: JAVA_TOOL_OPTIONS
  value: "-XX:MaxRAMPercentage=70
          -XX:+ExitOnOutOfMemoryError"
startupProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 5
  failureThreshold: 12   # up to 60s

What hetu watches for this
• Exit code 137 / OOMKilled events + reason
• Restart count vs time-to-stable (restart-to-heal signal)
• JVM heap/GC/metaspace (micrometer, JMX exporter)
• -Xmx / MaxRAMPercentage vs container limit mismatch
• Probe config vs observed warm-up time
• CoreDNS latency, SERVFAIL, ndots amplification
• connect refused/timeout to deps during first N seconds
• conntrack table / TCP retransmit spikes (node)
